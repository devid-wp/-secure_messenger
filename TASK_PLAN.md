# План доведения Secure Messenger до релиза

Цель: выпустить рабочий web/PWA-мессенджер, в котором личные и групповые сообщения и вложения передаются только через E2EE, сервер не получает plaintext, а установка и обновление воспроизводимы.

## 1. Стабилизировать текущую ветку

- [x] Завершить и проверить текущие изменения backend: rate limit, квоты KeyPackage и вложений, retention MLS envelopes, строгие API-схемы и миграцию `20260807_22`.
- [x] Удалить или переписать тесты, которые требуют старые файлы из `docs`, и убрать битые ссылки из корневого README.
- [x] Исправить зависание полного backend test suite; добиться стабильного прохождения всех тестов на чистой базе.
- [x] Зафиксировать поддерживаемые версии Python, Node.js, npm и Rust; проверить установку зависимостей только из lock-файлов.
- [x] Добавить единый CI gate: backend tests, migrations, frontend lint/typecheck/unit tests, Rust/WASM tests, production build и проверка отсутствия skipped security tests.

**Готово, когда:** чистый checkout устанавливается и собирается по README, миграции проходят с нуля, все автоматические проверки зелёные.

## 2. Закрыть E2EE как законченный пользовательский сценарий

- [x] Проверить полный MLS lifecycle для личных и групповых чатов: создание группы, Welcome/Add/Update/Remove Commit, смена epoch и доставка application messages.
- [x] Доделать multi-device: добавление устройства, синхронизация membership, отзыв устройства, немедленное завершение его сессий и невозможность читать новые сообщения.
- [x] Гарантировать fail-closed поведение: никакого plaintext fallback при ошибках WASM, рассинхронизации, offline/reconnect, повреждении vault или неизвестной версии протокола.
- [x] Довести локальный vault: создание, блокировка, разблокировка, смена passphrase, восстановление после перезагрузки, понятный сценарий потери vault без ложного обещания восстановления ключей.
- [x] Проверить шифрование вложений: имя, MIME, содержимое и ключ не попадают на сервер; оборванная загрузка и повторная отправка не создают битых сообщений.
- [ ] Добавить автоматические E2E-сценарии минимум для двух пользователей, двух устройств, offline/reconnect, группы, отзыва устройства, повреждённого vault и вложения.

**Готово, когда:** сетевые запросы, WebSocket, база, object storage и логи не содержат тестовый plaintext, а отозванное устройство не расшифровывает данные новых epoch.

## 3. Довести сам мессенджер до нормальной эксплуатации

- [ ] Проверить регистрацию, вход, refresh/logout, поиск пользователей, личные и групповые чаты, приглашения, роли, блокировки, сообщения, ответы, редактирование, удаление, реакции, вложения и стикеры.
- [ ] Исправить состояния загрузки и ошибок: повтор отправки, дубликаты, ordering, непрочитанные сообщения, reconnect WebSocket и восстановление после перезапуска вкладки.
- [ ] Разделить перегруженный `ChatApp.jsx` на небольшие компоненты и сервисы там, где это необходимо для устранения ошибок и тестируемости; не делать отдельный редизайн перед релизом.
- [ ] Проверить адаптивность и основные браузеры; оставить релизными только реально поддерживаемые варианты PWA/браузера.
- [ ] Устранить утечки секретов и персональных данных в логах, API-ошибках, telemetry и frontend console.

**Готово, когда:** основной сценарий «зарегистрироваться → создать/открыть чат → безопасно отправить и получить текст/файл → вернуться после перезапуска» работает без ручных обходов.

## 4. Подготовить production и выпустить

- [ ] Убрать development credentials из production-конфигурации; валидировать обязательные secrets, HTTPS origin, CORS, secure cookies, CSP и trusted proxy settings при старте.
- [ ] Подготовить production Compose/deployment: PostgreSQL, Redis, S3, health checks, миграции перед запуском, непривилегированные контейнеры, resource limits и безопасная сеть сервисов.
- [ ] Настроить backup/restore PostgreSQL и object storage, проверить восстановление и rollback миграции на staging.
- [ ] Добавить централизованные технические метрики и алерты без plaintext: доступность API/WebSocket, ошибки, latency, заполнение storage и срок действия сертификата.
- [ ] Провести dependency/container audit, устранить критические и высокие уязвимости либо явно заблокировать релиз.
- [ ] Создать минимальную актуальную документацию: установка, production deployment, backup/restore, security model, ограничения E2EE и действия при инциденте.
- [ ] Прогнать release candidate на чистом staging, выполнить E2E и smoke-тесты, собрать подписанный артефакт/образ, поставить версию и тег.

**Релиз разрешён, когда:** CI полностью зелёный, staging прошёл E2E, backup восстановлен на практике, production secrets не захардкожены, критических security-дефектов нет и есть проверенный rollback.

## Не блокирует первый релиз

- Нативные мобильные и desktop-клиенты.
- Звонки, stories, bots, federation и server-side поиск по сообщениям.
- Большой редизайн интерфейса.
- Новые функции, не нужные для надёжной переписки, управления устройствами и восстановления сервиса.
