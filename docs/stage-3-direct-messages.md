# Stage 3: рабочие личные сообщения

## Поиск пользователей

`GET /api/v1/users/search?q=<text>`

- запрос содержит от 2 до 64 символов;
- возвращается не более 20 результатов;
- поиск регистронезависимый;
- текущий, отключённые и placeholder-пользователи исключаются;
- `%`, `_` и `\` трактуются как обычные символы, а не SQL wildcard.

## Личные диалоги

- `GET /api/v1/chats/dm` возвращает только DM текущего пользователя;
- `POST /api/v1/chats/dm` принимает `{ "login": "bob" }`;
- повторный запрос для той же пары возвращает существующий чат;
- `chats.direct_key` и уникальный индекс защищают от дублей при гонке.

## История сообщений

`GET /api/v1/chats/{chat_id}/messages?limit=50&cursor=<cursor>`

Ответ:

```json
{
  "items": [],
  "next_cursor": null,
  "has_more": false
}
```

Страница выбирается keyset-условием, без `OFFSET`. Сначала запрашивается самая
новая страница; элементы внутри страницы расположены от старых к новым.
`next_cursor` непрозрачен для клиента и привязан к идентификатору чата.

## Идемпотентная отправка

WebSocket payload:

```json
{
  "chat_id": 42,
  "text": "hello",
  "client_id": "c356c862-546f-4f31-b7f1-d3a4695e0354"
}
```

Клиент создаёт новый UUID для логического сообщения и повторно использует его
при retry. Ограничение `UNIQUE(sender_user_id, client_id)` гарантирует, что
повторная доставка не создаст вторую строку. Повторное использование UUID с
другим чатом или текстом отклоняется.

## Миграции

- `20260727_03` добавляет уникальный ключ пары участников DM;
- `20260727_04` добавляет nullable `client_id`, сохраняя совместимость со
  старыми сообщениями, и уникальность UUID в пределах отправителя.
- `20260728_05` добавляет `server_seq`, уникальный и монотонный внутри чата;
- `20260728_06` добавляет постоянные квитанции доставки и прочтения.

## Порядок и состояния доставки

`server_seq` назначается сервером в транзакции создания сообщения. Счётчик
`chats.next_message_seq` блокируется на время записи; ограничение
`UNIQUE(chat_id, server_seq)` не допускает одинаковых номеров.

Состояния пользовательского интерфейса:

1. `sending` — сообщение находится в локальной outbox и ожидает ACK;
2. `sent` — сервер записал сообщение и вернул `message_ack`;
3. `delivered` — устройство получателя приняло событие и сервер сохранил receipt;
4. `read` — получатель открыл чат, сервер сохранил read receipt;
5. `failed` — ACK не получен или WebSocket оборван; сообщение остаётся в outbox.

Основные WebSocket-события:

```text
client -> server: send_message
server -> sender: message_ack
server -> recipient: message
recipient -> server: delivered
server -> sender: message_status(delivered)
recipient -> server: read
server -> sender: message_status(read)
```

## Восстановление соединения

- клиент хранит неподтверждённую outbox в `localStorage`;
- reconnect использует exponential backoff от 1 до 30 секунд;
- после подключения клиент повторяет outbox с исходными `client_id`;
- сервер возвращает существующее сообщение для уже сохранённого UUID;
- клиент заново загружает последнюю страницу истории;
- уникальность `(sender_user_id, client_id)` исключает дубликаты при retry.
